# Метод парной диагностики

Сид нового банка train — 9164107. Штатный генератор построил по 25 карт H1–H4, всего 100, с SHA-256 файла `da9f168ef715811273125a951986ab23719e078088e0c96cec816bcfbafa6f3e`. На классы пришлось по 25 карт каждого из четырёх семейств в совокупности. При генерации исключены 2 400 различных геометрий двух прежних банков E-0016 train. Отпечаток стен не зависит от меток, поворота и отражения. Отдельные потоки dev и confirmation зарегистрированы производителем под другими сидами. Покартовую проверку пересечений с закрытыми данными в этом опыте не проводили. [Генерация](bank.py) · [Банк](train.jsonl) · [Регистрация исходных потоков](../../E-0016/data/manifest.json)

До первого счёта записаны четыре ветви, входные файлы, порядок равных ходов, версии среды и библиотек. SHA-256 файла регистрации — `0688cd78e7163a74f232cde1b7bc44a230ee687b5308bfb1b78d79e587e860eb`. Для каждой нейронной ветви на каждой карте запускается чистый процесс CPU с одним потоком численных библиотек. Полный маршрут, имя карты, класс, сид и точная карта в канал выбора действий не поступают. Ветвь wave1 получает при инициализации только пару исходных регистров. Далее процесс получает по одному `Observation` и вызывает штатный `choose` на каждом физическом шаге. У frontier48 используется зарегистрированная точка входа основного режима. [Предрегистрация](preregistration.md) · [Хеши снимка](lock.json) · [Процесс политики](worker.py)

**Точный учитель.** В полном графе train-карты поиск в ширину проходит состояния «позиция, топливо, исправность» по возрастанию числа физических ходов. Состояние можно отбросить, если из той же позиции уже доступно более раннее или равное по времени состояние с обоими запасами не меньше. Кратчайшие геометрические длины до B и до соответствующего сервиса дают нижние границы. Приход на станцию пополняет соответствующий ресурс, а приход на B завершает поездку даже на последней единице. Пустой ход расходует оба ресурса и не пополняет ни один, поэтому он не нужен кратчайшему маршруту. Равенства разрешаются фиксированным порядком восьми направлений. Проверка продолжения из точки передачи учитывает все уже израсходованные шаги.

Исходное оптимальное число ходов сверяется с независимым значением генератора для каждой карты. Второй алгоритм достижимости проверяет каждого сохранённого свидетеля с лимитом, равным его длине, и с лимитом на единицу меньше. Затем команды свидетеля физически исполняются. Для недоступного продолжения второй поиск получает весь оставшийся лимит. [Выбор точных действий](oracle.py) · [Вторая проверка и агрегация](verify.py)

**Передача управления.** Граница — первый физический ход, после которого выполнены хотя бы одна заправка и один ремонт. Для продолжения с передачей управление получает новая политика при статусе `RUNNING`. Если до границы поездка завершилась, обе парные ветви сохраняют достигнутый исход. Передача обоих прежних показаний в wave1 использует `Observation` прямо перед последним ходом префикса. Первое решение получает штатное наблюдение после этого хода. Префикс повторяется через `env.step` в новой среде, после чего сравниваются память, окно, позиция, ресурсы, прежние показания, сервисы и остаток времени. Проверочный код дополнительно доказывает, что более раннего состояния с обоими посещёнными сервисами в префиксе не было. [Исполнение ветвей](driver.py) · [Синтетические границы](selftest.py)

**Как читать записи.** В файле каждой карты `teacher` и `own` содержат снимки на концах оптимального и собственного префиксов. Поле `steps` указывает длину префикса. `witness_suffix` содержит кратчайшее допустимое завершение при состоявшейся передаче. Пустое значение интерпретируется вместе с `kind`, различающим отсутствие передачи и отсутствие пути из достигнутого состояния. В `branches` записаны четыре полные последовательности команд со старта. Журнал показывает их как строки цифр, а SHA-256 вычисляется по исходным байтам со значениями 0–7. `observed` — количество клеток, в памяти которых уже записан известный тип, включая изначально известные сервисы. Идентификаторы всех пар с разными терминальными исходами перечислены в квитанции для каждой пары ветвей. [Сырые записи](episodes)

Проверка сохранённых результатов из корня Diplom использует проектное окружение. Сценарий `verify.py` повторяет физику по записям, сверяет обе границы, отпечатки весов и кратчайшие продолжения. Веса и зависимости для этой проверки закреплены в локальных снимках.

```powershell
$dir = 'results/verification-rl80/phase100-train'
& .\venv\Scripts\python.exe -B -X utf8 "$dir/selftest.py"
& .\venv\Scripts\python.exe -B -X utf8 "$dir/verify.py"
```
