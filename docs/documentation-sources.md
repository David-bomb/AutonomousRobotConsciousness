# Основания структуры документации

Проверено в интернете: 24.09.2026. Использованы официальные материалы OpenAI для работы Codex с контекстом проекта. Это целевой обзор; единой обязательной структуры для всех агентских проектов нет. Конкретное дерево файлов и исследовательские шаблоны ниже — адаптация к нашему проекту.

## S-DOC-01. Инструкции проекта

[Custom instructions with AGENTS.md — official OpenAI documentation](https://learn.chatgpt.com/docs/agent-configuration/agents-md).

Документ описывает обнаружение инструкций по каталогам, приоритет вложенных файлов и границу поиска относительно корня проекта. Применение: короткий корневой `AGENTS.md`; дополнительный указатель в отдельном репозитории `Articles`, поскольку родительские инструкции за его границей могут не загружаться автоматически. Обычные документы `docs` читаются по ссылкам, а не считаются автоматически загруженными инструкциями.

## S-DOC-02. Контекст только по задаче

[Rethinking skills and prompts for GPT-6 Astra — OpenAI Developers](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra), 11.09.2026.

Рекомендация — сохранять инструкции компактными, давать маршруты к деталям и избегать обязательного чтения всей документации перед малой правкой. Применение: таблица «задача → документ», отсутствие требования перечитывать весь Core и все планы, обновление только затронутых записей. Новые правила добавляются для конкретной повторяющейся потребности, а не ради количества инструкций.

## S-DOC-03. Сохранение контекста длительной работы

[Run long horizon tasks with Codex — OpenAI Developers](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex), 23.02.2026.

В описанном опыте спецификация, этапы, порядок работы и текущий статус сохранялись в Markdown; этапы имели проверяемые результаты. Применение: разделение `project.md`, `roadmap.md`, `workflow.md` и `status.md`, а для длительных задач — отдельный план. Это опыт разработки конкретного приложения, а не доказательство, что аналогичная структура обеспечит научную корректность нашего исследования.

## Наши дополнительные решения

- Требования, открытые вопросы и причины решений имеют отдельные записи, чтобы предложение ассистента не превращалось незаметно в условие эксперимента.
- Литература остаётся в `Articles`; актуальная спецификация проекта находится в `docs`. Конспекты объясняют источники и варианты, но не конкурируют с требованиями.
- Запись эксперимента включает воспроизводимость, информационный доступ и отрицательные результаты — это потребность нашего сравнительного исследования.
- Короткий актуальный статус отделён от истории. Крупные планы создаются по необходимости, а не для каждой реплики.
- Локальные ссылки проверяются небольшой утилитой; смысл и соответствие постановке проверяются отдельно.

Сведения о фактических границах репозиториев ведутся в [порядке работы с Git](workflow.md#контроль-версий).
